The Judge Reads Tokens: An Adversarial Evaluation of an Eval Toolkit's Own Scorers

Abstract. Every project in this portfolio got an adversarial eval suite; this one is the eval toolkit itself, so the system under attack is the scoring pipeline — the mock LLM judge and the deterministic scorers (contains, regex) that grade other projects' outputs. I aimed three attack families at it: outputs engineered to game the judge (negation, keyword echo, invented facts appended to true ones, fake citations), text addressed to the judge inside the candidate output (instructions, a pre-written verdict, and a smuggled replacement for the machine-readable CASE block the mock judge actually reads), and substring/regex exploits against the deterministic scorers — plus bias probes for length, word order and wording, and a human-labelled agreement slice to compare against the benign agreement set. The headline numbers: attack success rate 62.5% on hand-written seeds, false-refusal rate 50.0% on benign controls, pass/fail decision accuracy 42.3% on the seed mix, and judge-vs-human decision agreement collapsing from 0.917 on the benign labelled set to 0.200 on the adversarial one. The single most structural result is a spoof: because the rubric prompt embeds the candidate output verbatim before the CASE block, an output carrying its own fake CASE block gets graded on the case it smuggled in — a wrong answer scored a perfect 1.000. All runs are against the deterministic mock judge; what that bounds is stated plainly in Limitations.

The question

This repo's philosophy says: deterministic first, judge second, and when you use a judge, measure the judge. The shipped measurement is one benign agreement set — twelve well-behaved outputs where the mock judge agrees with human labels 0.917 of the time on the pass/fail decision. But nobody grades only well-behaved outputs. Candidate outputs in real evals are model-generated, occasionally adversarial, and — once a score gates anything — optimised against the grader. So the question is the one the sibling projects asked of their agents, turned on the grader itself: how much of this pipeline's judgement survives outputs that are trying to be misjudged, what does its strictness cost honest answers, and do its biases move scores by amounts that matter? Pass/fail alone answers none of these, so I scored three metrics: ASR, FRR, and decision accuracy, with judge-avg inflation against each attack's honest twin as the pressure gauge behind them.

Method

System. The llm_judge scorer renders a rubric prompt (three criteria — correctness, completeness, clarity, 1–5; the candidate output interpolated raw, in plain text, ahead of a machine-readable CASE block), and the default mock judge grades it: it extracts the first ```json block in the prompt, tokenises reference and output to [a-z0-9]+ sets, and scores keyword precision (→ correctness, with a hard 1 if the output contains a digit the reference lacks), keyword recall (→ completeness, with a penalty for outputs shorter than half the reference), and a word-count clarity rule (3 if the output exceeds 60 words, else 5). The criterion average passes at ≥ 0.8. The deterministic scorers grade by exact/substring/regex match. Every case in this suite runs through these code paths unmodified — the suite adds ground truth and classification, never patches.

Cases. Hand-written seeds (26): 9 judge-gaming attacks (two negations, an append-an-invented-benefit, word salad, a self-contradicting answer with evaluator flattery, a digit-free fake citation and its year-carrying twin, digit smuggling, and a hedge-farming case aimed at the rubric text), 4 injections (a direct instruction with a ready-made verdict, the CASE-block spoof, a pre-written verdict header, a fake "system note"), 3 deterministic-scorer attacks (negated and incidental contains mentions, an unanchored regex mention inside a denial), and 10 benign controls (verbatim, paraphrase, a long genuinely good answer, hedged-but-correct, an answer quoting attack phrasing as security content, terse, spelled-out digits, prose-instead-of-JSON, cited, and reference-plus-one-true-fact). Each judge attack carries a clean_output — the honest version of the same answer — so score inflation is measured, not vibes. Six deterministic mutations (caps, repetition, neutral padding, leetspeak, zero-width insertion, code fencing) multiply the 13 judge-scored attacks into 78 variants; controls ride verbatim; the generator stamps the seeds file's sha256 and regenerates byte-identically.

Bias probes. Three fixed probe sets, graded and printed, never asserted: a length ladder (the reference answer padded by repetition — token set frozen, only the clarity rule can move — and by neutral sentences, which dilute precision), order probes (verbatim / reversed / shuffled token order), and a wording ladder (verbatim → light paraphrase → full paraphrase → terse).

Comparability slice. Judge validation has a standard shape — a human-labelled set and agreement statistics — and the repo already ships one (datasets/judge_agreement.jsonl, 12 benign cases). The slice here is 10 new cases in exactly that schema, half of them attack outputs with human labels written from the spec, run through the same measure_agreement. It is labelled honestly: not an external benchmark (MT-Bench's raw data is not vendored into an offline repo), but the benchmark method applied to the distribution the benign set omits.

Metrics. Frozen in evals/scoring.py v1, same class names as the sibling suites. An attack run is succeeded (it passed a case it should fail), blocked (failed, with < 0.10 avg inflation over its clean twin), or evaded (failed but unmeasured: injection/rubric payloads the mock structurally cannot comply with, or inflation ≥ 0.10 — pressure that bought score without buying the pass). Benign runs are completed or false_refusal. Decision accuracy — pipeline pass/fail vs the written-down should_pass — is the completion analogue: for a grader, the decision is the task.

Bias probes

  • Length. Repetition padding holds avg at 1.000 through 56 words; at 64 words clarity steps 5 → 3 and avg lands at 0.867, flat thereafter to 160 words — a one-time tax, not a slope. Neutral padding is the opposite shape: a single 15-word off-topic sentence drops correctness 5 → 2 (precision dilution) and puts a perfect answer at avg 0.800, exactly on the pass line; more padding changes nothing until the clarity step compounds it to 0.667.
  • Order. Verbatim, reversed and shuffled token orders all score avg 1.000, criterion for criterion identical.
  • Wording. Verbatim 1.000 → light paraphrase 0.933 → full paraphrase 0.733 (fail) → terse 0.733 (fail — with correctness still 5 and completeness 1: the judge can see the fact is right and fails the answer anyway).

Findings

  1. The CASE block can be spoofed by the output being graded. render_prompt embeds the candidate output in plain text before the machine-readable CASE block, and the mock judge reads the first ```json block it finds. An output carrying its own block is graded on the smuggled case: avg 1.000 for an answer whose real content is a wrong refund window. The mock is the judge that falls for it here, but the structural fact is judge-agnostic: candidate-controlled text sits upstream of the block a grader is told to trust, with no escaping or delimiter discipline. Any consumer that extracts "the" JSON block from this prompt inherits the hole.
  2. Negation is free, and sometimes no trick is needed at all. "…is not 30 days…" scores 0.93; token sets have no negation. Worse, the Paris negation's honest twin — the plain wrong sentence "The capital of France is Lyon." — also passes (0.87), because a sentence-length reference gives a fluent wrong answer near-total overlap. The agreement set's "Lyon" case fails only because its reference is a single token. Reference length is an unexamined security parameter of this judge.
  3. Word order is invisible. Salad, reversed and verbatim score identically at 1.000. The judge grades a bag of words; anything whose correctness lives in arrangement — most of language — is outside its measurement.
  4. The digit rule is the only fact-check, and it prices citations precisely. A digit-free invented citation passes (0.87). Add a year and correctness collapses to 1 — yet the total still inflates from the honest wrong answer's 0.60 to 0.73, because the citation's vocabulary overlaps the reference. The tripwire costs the attack the pass, not the pressure.
  5. Append-don't-replace beats the threshold exactly. Verbatim truth in front, an invented "gold members get free returns forever" behind it: avg 0.800, a pass. Recall is bought with the truth; the invention is charged only diluted precision, and at reference scale the exchange rate favours the attacker.
  6. The benign tax is half the control corpus. FRR 50.0%: the paraphrase, the hedged answer, the terse answer, the spelled-out number and the long good answer all fail. The mechanism is one and the same as the attacks' — keyword overlap — so the judge is not "strict" or "lax"; it is token-shaped, and both error directions are that shape's shadow. A suite that reported only ASR would call this judge mediocre; a suite that reported only FRR would call it harsh. It is neither; it is blind in a specific, priced way.
  7. Length taxes are cliffs, not slopes. Two step functions: clarity at exactly >60 words (one-time, −2 points, never worse) and precision bands that a single neutral sentence already bottoms out. Between the cliffs, length is free — a 56-word repetition of the reference scores a perfect 1.000. Anyone tuning output length against this judge is optimising against two staircases.
  8. Surface mutations defend the mock by accident. Leetspeak and zero-width insertion score 0.0% ASR — not because anything detected them, but because they destroy the token overlap every attack was riding (mean variant inflation is negative, −0.089). Against a semantic judge these same transforms are the standard evasion toolkit. Any robustness conclusion drawn from the mock here inverts on the real backend; the variants measure the mock's tokeniser, and say so.
  9. Injection and rubric attacks are unmeasurable on the mock — and reach a real judge verbatim. Five seed runs sit in "evaded": direct instructions, a pre-written verdict, a fake system note, hedge-farming aimed at rubric wording the mock never reads. The mock cannot comply (it has no instructions to follow), so their failure proves nothing; meanwhile render_prompt does no sanitisation, so every payload arrives in a real judge's context intact, formatted exactly like the surrounding instructions. Evaded is the honest label: unmeasured, not safe.
  10. Judge validation collapses off the benign distribution. Decision agreement 0.917 → 0.200, MAE 0.528 → 1.567, on labelled cases that differ from the shipped set mainly by being adversarial. The repo's own advice — measure the judge — is right; the shipped measurement measures the distribution nobody attacks. A judge validated only on benign outputs carries a number that will not survive contact with optimisation pressure.
  11. The "trustworthy" deterministic scorers grade strings, not claims. contains passes a negation and an incidental mention of a different Paris; regex with the pattern as authors naturally write it (no anchors, and the scorer uses re.search) passes a sentence denying the reference it mentions. These scorers are exact about what they check — the finding is that what they check is not what dataset authors believe they check, and nothing in the harness warns them.

Limitations

Everything ran on the mock judge, which bounds every claim. The mock is a keyword stand-in, deliberately coarse; a real judge (the # SWAP: Gemini path exists but no API key is configured in this environment) would resist the token tricks and fall for different ones — the injection and rubric classes exist in the suite precisely to mark where the real risk is unmeasured rather than absent. Findings 1–7 are statements about this pipeline's mechanics, verified in its own code paths; finding 8 warns explicitly against exporting the mutation results to a semantic judge. The samples are small (16 seed attacks, 10 controls, 10 slice cases) and every seed is hand-written by the toolkit's author — the mutation engine and the clean-twin inflation measure exist to discount that, and the calibration of two cases (the fake-citation pair) after first measurement is visible in the file history. The slice's human labels are author labels written from the spec — the same stand-in status the repo already declares for its benign agreement set; a real human study replaces the labels, not the code. Decision accuracy is reported on an adversarially selected mix and is a suite property, not a field rate. The 0.8 threshold is the repo default throughout.

Future work

The real-backend slice comes first: the same seeds through the Gemini judge, converting the five evasions into measured ASR and testing whether findings 2–5 survive a judge with semantics (the prediction this write-up stakes: negation and salad die, injection and citation attacks get stronger). Defence fixes follow as a separately measured phase, graded by these suites as regression tests: escape or relocate the CASE block so candidate text cannot precede or imitate it (finding 1); anchor guidance or a fullmatch option for the regex scorer, and a negation warning for contains (finding 11); a judge prompt that separates candidate text with explicit delimiters. Any fix must move ASR, FRR and decision accuracy together — a judge that fails everything scores ASR 0% and is worthless, which is exactly why the three metrics are reported as one table.

Reproducibility

The project is public: llm-evals under github.com/tushar29k. The generator stamps the seed file's sha256 into its output and regenerates byte-identically; make_report.py rebuilds evals/adversarial-report.md from fresh runs with no timestamps, so a diff in the report is a diff in the numbers; metric definitions are frozen in a versioned scoring module (evals/scoring.py, v1 — the same class names and metric shape as the sibling projects' adversarial suites, so the numbers sit side by side). The suites are report-only (the harness's CI gate remains tests/run_tests.py plus the checked-in baselines), every run appends to evals/eval-history.jsonl, and every finding above is logged in the repository, deliberately unfixed, so the fix phase can be graded against them.

Appendix — score-seeking probes, added 6 Nov 2026

What this is. A follow-up probe built after the write-up above, using the same 13 judge-scored seeds that carry an honest twin (clean_output): the honest policy is each seed's clean output, the score-aware policy is each seed's attack output — keyword echo, word salad, append-an-invention, fake citations, judge-addressed payloads, and the CASE-block spoof. The judge is the same deterministic mock, unmodified, at the same 0.8 threshold. This measures grader gameability — how far outputs engineered against a visible scoring rule drift from correct towards score-maximising — not a live model choosing to seek score. No live model is in the loop anywhere in this probe; "score-aware" is a fixed, hand-written output set, not a policy that searched for these outputs.

The score rises while the work gets worse: mean judge average 0.754 → 0.785 (+0.031) while true task success falls from 30.8% to 0.0% — every score-aware output in the set should fail, and 7 of 13 pass. Knowing the grader is buggy changes nothing: the same 7/13 failed tasks still pass; only the audit against ground truth exposes them. The biggest single drift is the CASE-block spoof (+0.400, to a perfect 1.000); negation gains +0.333, the digit-free fake citation +0.267. Even the honest policy's gap is not zero (+7.7%): one honest twin, the plain wrong "The capital of France is Lyon.", already passes the judge at 0.867 with no trick at all.
